# Secret rotation runbook

Roadmap item T6. Every credential AdoptOps depends on, who holds it, and
how to replace it without an outage. Nothing in this list lives in the
repository: bindings are injected by Cloud Foundry, S/4HANA credentials
stay in destinations, and the pseudonymisation secrets stay in the
systems that generated them.

## Inventory

| Secret | Where it lives | Used for | Rotation |
|---|---|---|---|
| XSUAA client credentials | binding of `<space>-adops-basic-uaa` to the server and the approuter | token validation, token exchange, the user-management API | section 1 |
| PostgreSQL credentials | binding of `<space>-adops-basic-postgres` to the server and the db deployer | database access | section 1 |
| Destination service credentials | binding of `<space>-adops-basic-destination` | resolving the subscriber's S/4 destinations | section 1 |
| Connectivity service credentials | binding of `<space>-adops-basic-connectivity` | the on-premise proxy (Cloud Connector) | section 1 |
| Alert Notification, Cloud Logging credentials | bindings of the two instances | alerts, log shipping | section 1 |
| SaaS registry credentials | binding of `<space>-adops-basic-registry` | subscription callbacks | section 1 |
| S/4HANA technical users | the customer's destinations in the subscriber subaccount (docu/15 step 3 and 5) | usage reads, activation writes on DEV | section 2 |
| Pseudonymisation secret per S/4 client | `ZADO_CFG` in each S/4 system, generated by `ZADO_CFG_INIT` | user pseudonyms (docu/11) | section 3 |
| Tenant salt | `TenantSecrets` table, one row per tenant, generated on first use | second factor of the pseudonym | section 3 |
| Local hybrid bindings | `code/.cdsrc-private.json` on a developer machine (gitignored) | `srv:hybrid`, `db:deploy:postgres` | section 4 |
| Direct S/4 credentials for development | `ADOPTOPS_S4_DIRECT_USER` / `_PASSWORD` in a developer's shell | local runs against the lab system | section 4 |
| GitHub token for the release workflow | `GITHUB_TOKEN`, issued per run | attaching the archive to the release | nothing to rotate |

## 1. Service binding credentials

Cloud Foundry issues binding credentials per binding; a new binding gets new
credentials and deleting the old binding invalidates the old ones. Rotate
one service at a time, in `dev` first:

```bash
cf unbind-service adops-basic-srv-<space> <space>-adops-basic-<service> && cf bind-service adops-basic-srv-<space> <space>-adops-basic-<service>
```

```bash
cf restage adops-basic-srv-<space>
```

Where a service is bound to more than one app (XSUAA to the approuter,
PostgreSQL to the db deployer), repeat for each app and restage each.
Restaging is a short outage of that app; in `prod` do it during a
maintenance window or through a full blue-green redeploy (the MTA deployer
recreates the bindings of the new colour, and `cf deploy -a resume`
switches without downtime; see the release process).

Check afterwards: `/readyz` answers 200 (database), Target Systems > Test
Connection is `OK` (destination and connectivity), a forced task failure
reaches the Alert Notification instance (alerts), lines arrive in Cloud
Logging (logging), and a login works (XSUAA).

Service keys created for local development (`cds bind`) are separate
credentials; delete them when a developer leaves (`cf delete-service-key`)
and re-run `cds bind` for the others.

## 2. S/4HANA technical users

The password of the technical user is known only to the customer's basis
team and the destination. Rotation is theirs:

1. `SU01` on the S/4 system: new password for the technical user (or a new
   user, if the old one must be retired).
2. BTP cockpit, subscriber subaccount, the destination of that system and
   client: update the password, "Check Connection".
3. AdoptOps: Target Systems > Test Connection must report `OK`. Destination
   lookups are cached for five minutes; a check within that window may
   still use the old password.

During step 1 and 2 background tasks against that system fail with 401 and
raise `AdoptOpsTaskFailed`; run the rotation when no extraction or
activation is scheduled, or expect one alert per affected task.

## 3. Pseudonymisation secrets

Rotating either secret changes every pseudonym, so usage data collected
before the rotation no longer joins with data collected after it. Rotate
only for a reason (suspected disclosure, a policy period) and with the
AdoptOps administrator's agreement; start a fresh extraction afterwards.

- **S/4 secret** (`ZADO_CFG`): run `ZADO_CFG_INIT` with "Rotate existing
  secret" ticked in the affected client. Nothing else to do on the SaaS
  side.
- **Tenant salt** (`TenantSecrets`): delete the tenant's row from the
  table (the application has no rotate action); the next read generates a
  new random salt. Direct table access, so this is an operator action with
  an audit note in the daily log.

## 4. Developer machines

- `code/.cdsrc-private.json` holds service-key credentials for hybrid
  runs. It is gitignored; rotate by deleting the service keys (section 1)
  and running `cds bind` again. Never paste its content into an issue or a
  chat.
- The direct-access variables are environment variables of a shell
  session; they are refused in Cloud Foundry (S11). Rotate the lab user's
  password like any S/4 user.

## When a secret has been disclosed

1. Rotate it (sections above), in every space it applies to.
2. Check the audit chain (`verifyAuditChain` on the Audit Log page) and
   the Cloud Logging dashboard for calls in the exposure window.
3. Record what was rotated and when in the admin tracker's daily log; the
   audit chain records the application-level actions of that window.
